# StepWise Repository Guidance / StepWise 仓库指引

## Scope and precedence / 适用范围与优先级

- This file applies to the entire StepWise repository tree unless a deeper `AGENTS.md` provides more specific instructions.
  中文：本文件适用于 StepWise 仓库全树；若更深层目录存在更具体的 `AGENTS.md`，则以其为准。
- Within the StepWise project, these rules supplement and, where they are more specific, override outer workspace guidance; all other compatible outer rules still apply.
  中文：在 StepWise 项目范围内，本规则补充外层工作区指引，并在内容更具体时覆盖外层规则；其他相容的外层规则仍然有效。

## Project truth and boundaries / 项目事实与边界

- StepWise is a modular engineering prototype for gait screening, not a medical device or clinical system.
  中文：StepWise 是用于步态筛查的模块化工程原型，不是医疗设备或临床系统。
- Never claim clinical accuracy, diagnostic capability, production users, public deployment, production traffic, or production scale.
  中文：严禁声称临床准确率、诊断能力、生产用户、公开部署、生产流量或生产规模。
- Active source code lives under `src/stepwise`.
  中文：活跃源码位于 `src/stepwise`。
- `archive/course-materials` preserves historical course materials only; it is not a runtime dependency and should remain read-only unless the user explicitly requests otherwise.
  中文：`archive/course-materials` 仅保存历史课程材料，不是运行时依赖；除非用户明确要求，否则应保持只读。
- Do not add a database, authentication, a distributed queue, long-term cloud storage, a public deployment, or a new clinical algorithm unless the user explicitly expands the scope.
  中文：除非用户明确扩展范围，否则不得添加数据库、认证、分布式队列、长期云存储、公开部署或新的临床算法。

## Canonical architecture and shared logic / 标准架构与共享逻辑

- `AnalysisService.analyze(walking_path, standing_path, output_dir, config)` is the only business entry point.
  中文：`AnalysisService.analyze(walking_path, standing_path, output_dir, config)` 是唯一业务入口。
- API, CLI, batch, and worker adapters must call that entry point and must not copy or fork the analysis algorithm.
  中文：API、CLI、批处理和 worker 适配器必须调用该入口，不得复制或分叉分析算法。
- Keep domain models and service contracts shared across the API, CLI, and Mini Program; transport and UI adapters must not create competing business rules.
  中文：API、CLI 和小程序应共用领域模型与服务契约；传输层与界面适配器不得另建相互竞争的业务规则。

## Stable interface contracts / 稳定接口契约

- Preserve exactly these five HTTP routes unless an explicitly approved interface change includes migration and contract tests:
  中文：除非明确批准的接口变更同时包含迁移方案和契约测试，否则必须保持以下五条 HTTP 路由不变：
  - `POST /api/v1/analyses`
    中文：创建异步分析任务。
  - `GET /api/v1/analyses/{run_id}`
    中文：查询分析状态。
  - `GET /api/v1/analyses/{run_id}/result`
    中文：获取分析结果。
  - `GET /api/v1/analyses/{run_id}/artifacts/{name}`
    中文：下载允许列表中的分析产物。
  - `GET /healthz`
    中文：检查服务健康状态。
- Keep API errors in the stable shape `{"error":{"code":"...","message":"..."}}`.
  中文：API 错误必须保持稳定结构 `{"error":{"code":"...","message":"..."}}`。
- Preserve `413` for oversized uploads, `422` for invalid text, timestamps, or mapping, `429` for a full queue, `409` for a result that is not ready, and `404` for unknown jobs or artifacts outside the allowlist.
  中文：保持以下状态码语义：上传过大为 `413`，文本、时间戳或映射无效为 `422`，队列已满为 `429`，结果尚未就绪为 `409`，未知任务或不在允许列表内的产物为 `404`。
- Preserve CLI `analyze` and `batch` exit codes: `0` for success, `2` for invalid input, and `1` for an unexpected analysis failure.
  中文：保持 CLI `analyze` 和 `batch` 的退出码：成功为 `0`，输入无效为 `2`，意外分析失败为 `1`。
- Preserve the six supported environment variables: `STEPWISE_DATA_DIR`, `STEPWISE_MAX_UPLOAD_BYTES`, `STEPWISE_ANALYSIS_TIMEOUT_SECONDS`, `STEPWISE_MAX_WORKERS`, `STEPWISE_MAX_QUEUE`, and `STEPWISE_RESULT_TTL_HOURS`.
  中文：保持六个受支持的环境变量：`STEPWISE_DATA_DIR`、`STEPWISE_MAX_UPLOAD_BYTES`、`STEPWISE_ANALYSIS_TIMEOUT_SECONDS`、`STEPWISE_MAX_WORKERS`、`STEPWISE_MAX_QUEUE` 和 `STEPWISE_RESULT_TTL_HOURS`。

## Runtime integrity and regression tests / 运行时完整性与回归测试

- Any change to workers, queue limits, killable hard timeouts, UUID run directories, atomic manifests, artifact allowlists, TTL cleanup, or restart recovery must include focused regression tests.
  中文：任何涉及 worker、队列限制、可终止的硬超时、UUID 运行目录、原子 manifest、产物允许列表、TTL 清理或重启恢复的变更，都必须包含针对性回归测试。
- All JSON outputs and persisted manifests must be strict JSON; `NaN` and `Infinity` are forbidden.
  中文：所有 JSON 输出和持久化 manifest 都必须是严格 JSON；禁止出现 `NaN` 和 `Infinity`。
- Make the smallest scoped change, keep it typed, and write or update tests before implementation for behavior changes.
  中文：变更应保持最小范围和类型完整；涉及行为变化时，应先编写或更新测试，再实现功能。
- After running tools or tests, the worktree must contain only intended changes; remove only artifacts generated by the current task and never disturb user-owned changes.
  中文：运行工具或测试后，worktree 中只能保留预期变更；仅可清理当前任务生成的产物，绝不能影响用户已有改动。

## Git and review workflow / Git 与评审流程

- Use a `codex/*` branch and an independent worktree for non-trivial work.
  中文：非平凡工作必须使用 `codex/*` 分支和独立 worktree。
- Integrate through a pull request and successful CI; do not work directly on or bypass `master`.
  中文：必须通过 PR 和成功的 CI 集成；不得直接修改或绕过 `master`。
- Preserve tracked and untracked user changes, avoid bulk staging, and never use destructive Git operations such as `git reset --hard` or forced checkout cleanup.
  中文：保护用户所有已跟踪和未跟踪的改动，避免批量暂存，严禁使用 `git reset --hard` 或强制 checkout 清理等破坏性 Git 操作。

- Run `ruff check src tests`.
  中文：运行 `ruff check src tests`。
- Run `mypy src/stepwise`.
  中文：运行 `mypy src/stepwise`。
- Run `pytest --cov=stepwise --cov-report=term-missing`, and keep total coverage at or above 80%.
  中文：运行 `pytest --cov=stepwise --cov-report=term-missing`，并确保总覆盖率不低于 80%。
- Run `node --test tests/js/*.test.js`.
  中文：运行 `node --test tests/js/*.test.js`。
- Docker and CI validation must perform a real image build and a real container flow covering health, upload, status polling, result retrieval, and artifact download.
  中文：Docker 与 CI 验证必须真实构建镜像并运行容器流程，覆盖健康检查、上传、状态轮询、结果获取和产物下载。

## Evidence and resume claims / 证据与简历陈述

- The presence of a workflow file does not prove that CI has run or succeeded.
  中文：workflow 文件存在并不能证明 CI 已运行或成功。
- Docker, GitHub Actions, and other technical claims require evidence tied to a real commit and a successful workflow run.
  中文：Docker、GitHub Actions 及其他技术陈述必须有对应真实提交和成功 workflow 运行的证据。
- Only after that evidence exists may confirmed claims in the workspace-root `resume_data.yaml` be updated, followed by the required resume rebuild and audit; never place planned or unverified claims in formal materials.
  中文：只有具备上述证据后，才可更新工作区根目录 `resume_data.yaml` 中的 confirmed 陈述，并按要求重新构建和审计简历；正式材料中绝不能出现 planned 或未经核验的陈述。
- Do not record dynamic facts such as a current commit SHA, test count, branch state, or application status in repository guidance or durable project claims.
  中文：不得在仓库指引或长期项目陈述中记录当前提交 SHA、测试数量、分支状态或申请状态等动态事实。

## Privacy and repository hygiene / 隐私与仓库卫生

- This is a private repository, and CI may use only anonymous synthetic fixtures.
  中文：这是私有仓库，CI 只能使用匿名合成 fixture。
- Never commit real participant data, local absolute paths, teammate identities or private details, tokens, secrets, private configuration, or live deployment URLs.
  中文：严禁提交真实参与者数据、本机绝对路径、队友身份或隐私信息、token、secret、私有配置或 live deployment URL。
- Do not add generated `outputs/`, `uploads/`, or `reports/` directories to Git.
  中文：不得将生成的 `outputs/`、`uploads/` 或 `reports/` 目录加入 Git。
- Do not write participant, teammate, or other third-party identities or private details into project documentation or generated output, and do not add private identity information discovered in this repository to formal materials; this restriction does not apply to necessary, confirmed resume-owner identity information in the workspace-root `resume_data.yaml`. Keep private repository URLs, current branch SHAs, dynamic test totals, and application statuses out of durable project guidance and claims.
  中文：不得将参与者、队友或其他第三方的身份或私人资料写入项目文档或生成物，也不得把从本项目仓库发现的私人身份信息新增到正式材料；此限制不适用于工作区根目录 `resume_data.yaml` 中经确认的简历所有者必要身份信息。私有仓库 URL、当前分支 SHA、动态测试总数和申请状态不得写入长期项目指引或陈述。
- Before finishing, check the diff for placeholders, secrets, contradictions, unintended files, and unsupported claims.
  中文：完成前必须检查差异中是否存在占位符、秘密、矛盾、意外文件或缺乏证据支持的陈述。
