## 2. 开跑前必须先读出来的东西

**本 brief 中出现的任何配置值都只是参考，以当前 master 的实际默认值为准。**

从源码读出并写进报告：

- `max_workers`（记为 **W**）
- `max_queue`（记为 **Q**）
- `timeout_seconds`
- `max_upload_bytes`
- `result_ttl_hours`
- 轮询/状态接口的实际路径与返回结构
- 429 / 413 / 422 / 409 / 404 各自的触发条件

同时记录：CPU 核心数、内存、Python 与依赖版本、磁盘余量、电源状态。

服务 data root 优先使用 `C:\swlt`，失败时依次尝试用户主目录下的 `swlt` 与
`%TEMP%\swlt`；每项均配套同级 `swlt-rejected`。候选必须通过写入、flush、读取、
删除探针和安全根校验，并按实际 resolved 根重新计算最长服务路径。最长候选路径
不得超过 220 字符。所有递归删除只允许解析后的目标严格位于实际 work root 下，
使用路径组件级包含检查；work root 本身、驱动器根、用户主目录、仓库路径、兄弟
前缀和经 junction 解析后逃逸的目标均不得进入递归删除。

开跑前分别以单客户端、单作业、全新服务进程校准 30,000 与 360,000 样本。
上传阶段以 10 ms 采样 generator RSS，其余阶段以 50 ms 采样；分别记录 input bytes、
单请求 generator RSS 增量峰值、worker 峰值与 parent 峰值，不使用猜测放大系数。
令 W 为实际 worker 数，两个独立门槛为：

- `threshold_30k = worker_peak_30k × W + parent_peak_30k + gen_peak_30k_C20 + 2 GiB`
- `threshold_360k = worker_peak_360k × W + parent_peak_360k + gen_peak_360k_C2 + 2 GiB`

两次校准服务完全退出后，间隔 1 秒读取三次 available memory 并取最小值。达到
`threshold_30k` 才运行 30k 矩阵、故障测试与 A2；达到 `threshold_360k` 才运行
360k C=W。单个子集不达标则写入 `skipped_points`，另一个继续；两个均不达标或
任一校准失败则停止报告。2 GiB 项就是下述运行时地板。

每个 repetition 以 1 Hz 记录可用内存、pagefile used 与磁盘余量：任一采样可用
内存低于 2 GiB，或窗口内 pagefile used 的最大值相对起始值增长超过 200 MiB，
该并发点标注为不可引用，但其余点继续。

磁盘余量任一时刻低于 20 GiB 则中止整个 suite。每个 repetition 前后均记录
余量；有明确低空间或磁盘 I/O 证据的 `analysis_failed` 属于环境失败，该点不可
引用且不得登记为并发缺陷。

## 3. 要回答的五个问题

1. **饱和吞吐**：每分钟能完成多少次分析？在哪个并发度饱和？
2. **背压临界点**：队列在哪个并发度打满？429 **是否真的返回**，还是请求被静默排队？
3. **延迟构成**：端到端 p50 / p95 是多少？其中**排队等待**占多少、**计算**占多少？
4. **故障隔离**：一个 worker 被 120 s 超时杀掉时，其他在跑的请求是否受影响？队列是否正常排空？有没有残留进程？
5. **并发下的正确性**：并发提交同一份输入，**所有结果必须完全一致**。

第 5 条最重要。吞吐数字如果建立在错误结果上，一文不值。

## 4. 压测工具设计

新增 `bench/load_test.py`（或同等位置），**不改动任何现有源码**。

### 4.1 闭环模型

N 个虚拟客户端并发。每个客户端循环：提交 → 轮询至终态 → 记录 → 立即提交下一个。

**必须在报告里写明：这是闭环（closed-loop）测量，衡量的是服务容量，不是固定到达率下的用户感知延迟。** 闭环下客户端会自然等待，因此不存在 coordinated omission，但也不能把这些 p95 当作真实用户延迟。

### 4.2 轮询间隔

**显式设定为 50 ms，并写进报告。** 轮询间隔直接决定延迟测量的分辨率——报告中必须声明：测得的端到端延迟含最多一个轮询间隔的量化误差。

### 4.3 负载生成器与服务共用一台机器

这是已知限制，必须写进报告：W 个 worker 进程 + 父进程 + 负载生成器争抢同一批核心。记录核心数，并在并发度接近核心数时明确标注该限制。

生成器必须是 async（`httpx.AsyncClient`），不得用忙等或线程池轮询。

每个 repetition 必须使用全新 data root 和全新服务进程。原始结果记录服务 PID、
process create time、启动/health-ready/停止时间、退出码及 worker PID；确认旧服务及
其 descendants 已退出后，才可开始下一次 repetition。

以 1 Hz 记录负载生成器进程自身 CPU，占用按单核计算（100% 表示一个逻辑核）。
连续 10 秒的滚动中位数超过 80% 时，该点标注为 `generator-limited`，吞吐不可引用。

### 4.4 输入

录音文件**生成一次、全程复用**，不在测量中重建。主工作负载用 **30,000 样本**（当前约 1.2 s 计算量），另在 360,000 上取一个饱和确认点。

记录每个输入文件的 SHA-256。

## 5. 测量矩阵

并发度按实际读出的 W 和 Q 取：

| 并发度 | 目的 |
|---|---|
| 1 | 单请求基线，与现有 6.6074 s（360k）/ 对应的 30k 数字对照 |
| W | 恰好占满 worker |
| W + Q | 恰好占满 worker + 队列 |
| W + Q + 2 | **应当开始返回 429** |
| 2 × (W + Q) | 明显过载 |

每个并发度：**丢弃前 10 个完成的作业作为预热**，然后至少采集 **200 个完成作业**。
并发度 1 和 W 的最大正式窗口为 **300 s**；其余并发度为 **120 s**。窗口内不足
200 个则如实说明样本数。每个并发度跑 **3 次**，每次使用全新服务进程，取中位数，
报告 spread。

**任一并发度的吞吐 spread 超过 20% → 该并发度标注为不可引用**，其余保留，整体不重跑。

每个并发度之间清理 artifact 输出目录并记录磁盘余量。

30k 与 360k 子集是否执行由第 2 节的两个实测门槛独立决定；跳过的子集必须记录
available memory、所需门槛及完整代入算式，不得把未测点写入吞吐表。

整个矩阵与故障测试完成后，以相同口径和全新服务进程再跑一次 30,000 样本、
并发度 1（A2）。A2 吞吐落在开头三次并发度 1（A1）的 min-max 闭区间内，判定
会话未检测到漂移；落在区间外则报告相对 A1 中位数及最近边界的漂移幅度，并将
A1 之后的点标记为 `session-drift-affected`。不自动重跑。

## 6. 并发下的正确性检查（不可跳过）

同一份输入并发跑出的所有成功结果，其关键字段必须**完全一致**。

做法：对每个成功作业的结果取一个稳定摘要（例如对 `steps` 表的全部数值列与 session metrics 做规范化后的 SHA-256），并要求：

- 所有成功作业的摘要**完全相同**
- 若出现任何不一致 → **立即停止压测，保留两份完整结果与 run_id，作为最高优先级缺陷报告**

这检查的是作业间的串扰（共享临时目录、artifact 路径冲突、manifest 覆盖）。这类 bug 只在并发下出现，正是压测存在的理由。

## 7. 故障模式测试

在主矩阵之外，单独跑：

### 7.1 超时隔离
构造一个必然触发 `timeout_seconds` 的作业（例如超大输入，或临时注入的慢 runner——**注入方式不得修改产品源码**，只能通过 `JobManager(runner=...)` 这类既有注入点）。断言：
- 该作业终态为 `analysis_timeout`
- 同期其他作业正常完成
- 队列正常排空
- 无残留子进程（测量前后对比进程数）

### 7.2 TTL 清理与写入并发
把 `result_ttl_hours` 设为极小值（通过构造参数，不改源码默认值），让 TTL 清理与作业提交并发运行。

**这是最可能暴露 Windows manifest 文件锁竞态的场景。** PR #11 的两次完整 coverage 运行各出现过一次该竞态；PR #12 未复现。若在此复现：
- 记录完整 traceback、run_id、时间点、并发度
- 保留到 `bench-data/rejected/<timestamp>-manifest-race/`
- **不要修**，报告即可

### 7.3 背压真实性
在 `W + Q + 2` 及以上并发度，断言：
- 确实收到 429（数量 > 0）
- 429 是**立即**返回的（记录其响应时间中位数），而不是排队后才拒绝
- 被 429 拒绝的请求没有在服务端留下任何残留（作业目录、manifest）

429 后客户端固定等待 500 ms 再重试。429 数量是并发度、退避和上传/验证耗时的
函数，不得表述为拒绝率或任何单位时间速率。对于出现 429 的 repetition，同时报告
标称并发和“有效并发”：正式窗口内持有已接受在途作业的客户端数量的时间加权平均值。
该点吞吐必须注明是在此重试策略及有效并发下测得。若矩阵未触发 429，可运行独立
30 s 兜底 burst，但不得混入吞吐表。

### 7.4 健康检查
全程以 1 Hz 独立探测健康检查端点，报告其在各并发度下的 p50 / p95 / 最大值。
Phase 1 有"最大上传校验期间 < 250 ms"的既有断言，**那是单请求场景，不得直接套用到并发场景**。

## 8. 必须报告的内容

每个并发度一行，全部给**绝对数值**：

- 两次内存校准的输入字节数、单请求 generator RSS 增量峰值、worker/parent 峰值、
  两个门槛的完整代入算式，以及间隔 1 秒的三次 available memory 读数

- 完成作业数、429 数、各错误码计数
- 吞吐（作业/分钟），3 次的中位数与 spread
- 实际正式样本数 n，与延迟统计并排列出
- 当该 repetition 的有效 n ≥ 100：端到端 p50 / p95（毫秒）
- 当有效 n < 100：端到端 p50 / p90 / 最大值，并标注替代口径
- 排队等待 p50 / p95，与计算耗时 p50 / p95 **分开列**
- 父进程峰值 RSS 与 worker 峰值 RSS 之和
- 健康检查 p50 / p95 / max
- 每个 repetition 的服务 PID 与 process create time
- 负载生成器 CPU p50 / p95 / max 及 10 秒滚动中位数峰值（按单核计算）
- 可用内存最小值；pagefile used 起始、结束、最大值
- PDH `Pages Input/sec` / `Pages Output/sec` 中位数与最大值；硬缺页读入页数与
  磁盘读操作数分开报告
- 每个 repetition 的磁盘余量起止
- 出现 429 时的有效并发及“在所述重试策略下测得”的吞吐标注

上述样本量规则分别应用于端到端、排队、计算、429 响应和健康检查各自的有效 n。
未观察到 `running` 的作业，其排队/计算拆分记为缺失，不推算。三次 repetition
使用不同分位数口径时，不得把 p95 与 p90 合并；摘要写 `mixed; see repetitions`。

360,000 样本、C=W 的作业延迟不报告任何分位数：列出全部正式端到端 raw values、
其中位数和实际 n；排队/计算只列 raw values 与缺失数。独立健康探针仍按自身 n
应用上述规则。

另外单列：
- 第 6 节正确性检查的结论（摘要是否全部一致，样本数）
- 第 7 节四项故障测试的结论
- 所有限制与已知偏差（同机负载生成、轮询量化、笔记本热漂移）

## 9. 不得声称的事

- 不得把笔记本上的吞吐说成生产吞吐。报告与后续 bullet 里应强调**形状**（在哪里饱和、429 在哪里开始、排队占比如何变化），而非绝对 rps。
- 不得声称"零延迟代价"或"线性扩展"。
- 不得把闭环 p95 说成用户感知延迟。
- 不得把 429 数量说成拒绝率；它取决于明确记录的 500 ms 客户端退避。
- 不得把 Phase 1 的单请求健康检查断言套用到并发场景。
- 不得把任何一次的数字与历史会话的数字相加减。

## 10. 发现缺陷怎么办

**报告，不修。**

- 正确性不一致（第 6 节）→ 立即停止，最高优先级报告
- manifest 竞态 → 记录证据，继续压测
- 429 未按预期返回、超时未隔离、进程残留 → 记录，继续压测
- 崩溃导致压测无法继续 → 保留证据，停下报告

任何修复都走**独立 PR**，且必须先由 owner 审阅缺陷报告后再动手。这是防止本任务演变成 Phase 3 的硬边界。

## 12. 修订记录

本节记录 owner 在执行前批准的操作指令修订；上文已就地改正，以下不是覆盖层。

1. **内存与 pagefile gate。** 原 8 GiB 固定阈值没有测量依据，已由 30k 与 360k
   单作业实测导出的两个独立门槛取代；保留测量中 2 GiB 地板和 200 MiB pagefile
   增长 gate，防止换页静默污染延迟分布。证据保留规则只约束规则生效后产生的
   数据，不追溯，也不得从会话日志重建已删除的测量证据。
2. **样本量、窗口与分位数。** 删除 p99；有效 n 不足 100 时改报 p90 与最大值，
   360,000 样本点改报全部 raw values；C=1/W 窗口延长到 300 s，避免用最大值附近
   的噪声冒充高尾分位数。
3. **429 的重试策略依赖。** 固定 500 ms 退避，禁止报告拒绝率，并增加有效并发，
   因为 429 数量和该点实际施压强度由客户端策略共同决定。
4. **生成器 CPU gate。** 增加按单核计算的 80% 持续占用判据，排除吞吐实际受
   负载生成器限制的测量点。
